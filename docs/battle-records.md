# 对战记录：开发检查版说明

## 2026-11-02晚间更新（优先于下方历史约定）

完整说明见[成长、赛季筛选、进化链规则与条件反推](<battle-growth-seasons.md>)。本轮新增双方选定特性/技能成长有效样本统计、通用进化链及首领匹配、15条随包默认分类和显式载入草稿入口、季/周时间范围与敌方名次双滑块、按实际执行次数计算的敌方技能使用率，以及带+10个体前提标记的分项配置推断。组件不再显示初始技能携带和生命个体/性格联合面板；原始证据仍保留。聚能及18属性愿力图标随软件分发。

实际冻结战报验证：内置规则下归狼王；敌方13次已确认技能执行可统计；6只敌方的初始生命项在+10假设下唯一，其他属性条件不足；成长缺少完整效果证据，不填0。用户已有自定义规则不自动覆盖，载入内置规则先二次确认草稿、再显式保存。原始283事件与个人/图鉴资料不变。

## 交付状态与边界

导航：**伤害计算 → 对战记录 → 伤害曲线**。

本版实现独立战报存储、规范化文件导入、对局详情/时间线、按有效样本统计、组合规则、条件推断、临时伤害快照，以及手动连接外部本机RKPP中继。最初验证使用隔离合成记录；后续获授权接入本机RKPP，并对用户已有一场记录做身份恢复。**测试仍使用临时数据库，不把合成记录放入真实战报库。**

这不是“当前游戏任意对局已能自动完整还原”的承诺。特别是原始协议的技能/精灵ID映射、实际伤害数值、首发、敌方个体/性格、分数/名次与永久成长条件，还需要获授权的完整实际样本核验。未知不补0，多候选不冒充唯一值。

- 我方阵容整行点击展开/再次点击收起，子项改为该精确初始ID多重集合对各敌方体系的我方战绩；不同我方阵容不混计。共享筛选先应用，所有展开/详情读取当前响应，不额外请求或回写记录。
- 敌方样本只分敌方精灵表现/敌方阵容统计/环境统计三块。表现重用纯side-aware引擎，不交换或改写规范化原始事件/约束/非对称速度证据。敌方第一列为携带局数、进场次数、携带率、精灵胜率，不显示登场局数、没有精灵详情入口；其余五列对应我方最新指标。携带率分子分母同取完整且身份已确认的敌方阵容样本，按场/物种去重；精灵胜率是敌方携带该精灵时敌方获胜（原始我方loss）/携带且结局已知局数，未登场仍是携带，未知结局不当失败。501专属率同样在第五列，成功后胜率取敌方视角。
- 规则编辑仅从敌方阵容统计标题旁的阵容规则CSS弹窗进入。必含monsterIds全满足，excludedMonsterIds任一出现则排除；按已保存数组顺序只归入首条匹配规则，阵容完整但没有命中则为保留类型__other__（其他）。缺失/未映射阵容不冒充其他。规则名称不是分类身份，战中变形和换场不改变初始体系。既有SQLite position保持优先级，无数据表版本迁移；不自动保存示例或预置规则。
- GET rules返回rules及revision；现代编辑器显式保存提交完整有序列表和baseRevision，服务同一事务内比较当前revision，过期409且不覆盖。新增/删除/编辑/上移下移先保留草稿；关闭/重开按生命周期重建公共选择器，不让脱离DOM的控件复用失效。保存中关闭不等于撤销提交；真实失败、重试和重新读取仍可用。
- 敌方体系表依次为规则核心头像、其他队友头像/选择率、局数、我方对阵胜率/结局样本、平均回合、平均用时。其他队友率按该体系各局是否携带计，同场同种一次，核心不重复列；多队友率总和不要求100%。点击整行展开该体系各组件的初始技能携带与个体/性格分布，再点收起；同种精灵在不同体系严格分开。
- initialSkills是可选初始技能槽证据（skillIds本地稳定ID、complete是否完整），缺失绝不是空配招。只有同种所有初始实例配招完整的场次参与携带率分母，按局取技能并集；使用记录、过山车后的技能、图鉴学习面或玩家个人配置不得代替初始携带。明确初始配招的部分信息可补全，但两个已知冲突拒绝。个体/性格仅direct或unique且同种实例一致的值纳入；生命个体/性格联合分布必须同一实例同时确认，不能相乘边际比例伪造双生命，54等精确个体不布尔化。
- 环境图、敌方体系表、我方对体系战绩共用同一互斥归类。环境占比为各体系局数/有效完整敌方阵容局数，总和100%；无分母不画伪扇区。公共日期/结果/精灵/体系/段位筛选一致，体系筛选也按最终首条归属判断。
- 当前真实冻结战报有双方完整初始阵容，敌方开局技能槽及已规范化个体/性格未公开，组件配置必须显示未确认，不用施放记录充作携带。full_for_data_level仅是相应披露级别完整，不能推定完整配招。此轮不修改真实战报/图鉴/个人资料；测试只用隔离副本和合成fixture，未操作浏览器或原生窗口。

- 第一栏保持携带/登场/进场，移除“部分记录”标记。第二栏依次为击杀数、每死攻击数、造成克制/抵抗/通常伤害次数、伤害总量；第三栏为攻击/状态/防御实际执行次数、攻击被应对率、状态被应对率、防御成功率；第四栏为受击数、每死受击数、受到克制/抵抗/通常伤害次数、受击总量。已记录的量及携带场均继续分开；每死和各成功率不随总计/场均重复除携带局数。
- 每死指标按累计实际攻击/受击行动数除以该精灵累计明确死亡数；死亡不是普通退场。死亡即使来源未知、未确认在场，也可按直接倒下证据统计；HP0变形回血不算死亡，倒下加补位不重复，零死亡显示—。
- 状态次数包含明确的聚能行动（系统700001000），不含纯资源同步/被动。三类次数计实际执行；三类率以明确尝试为分母（包括被打断）。攻击/状态被应对数按被敌方成功应对的本类行动去重，不按敌方使用了哪种技能归类。
- 防御成功须防御类技能明确应对了敌方已确认攻击，普通施放/空防不算；被拦下的攻击可以已打断，不要求造成HP损失。先完成所有行动分类，再计算此关联，不能依赖map遍历顺序。当前四次己方防御成功由原始匹配受击has_shield=true进一步核对，不能从伤害小或damage_change猜防御减免；damage_change包含溢出截断，不是减伤量。攻击/状态技能的应对不算防御成功。

## 我方表现与阵容统计（2026-11-01晚间）

样本统计内分“我方样本统计／敌方样本统计”，默认我方，共用原筛选条件。敌方原有统计与完整行动样本规则不变。我方新增只读观察统计，提供总计／场均切换，不写个人配置、编队或战报派生值。

- 按每局初始本地精灵ID归集表现，同实例变形不另造携带队员。携带局数按精灵/对局去重；登场局数、进场次数分开。首发和再次入场计进场，不因形态改变计新入场；后排同步/被动不证明入场。明确退场可证明登场及离场，但缺少入场记录时不制造一次入场；单独倒下不能证明此前在前台。
- 每项计数、伤害量的场均分母均为携带局数，不是登场局数。部分记录也显示明确观测到的事件量及其携带场均，但保留覆盖/未解析数量，不宣称完整战绩，不把缺失当作确定没发生。
- 攻击次数只计已执行攻击行动，不计聚能、防御、变化、中断等非攻击；多段/多目标同一行动总攻击次数为1。造成及受到的克制、抵抗、通常伤害次数按行动和该类去重，同一次混合关系行动可在多个类别出现，但总攻击数不重复。使用“通常伤害”，不与普通系名称混淆。
- 属性关系优先直接combat.effectivenessClass。原始SkillRestraintType负值表示抵抗、正值克制、0通常，按正确int32解码；不从伤害大小或当前静态属性盲推。只知分类时不捏造具体数值倍率。未知关系保留覆盖缺项，不归通常。
- 伤害量按实际HP减少，不累计报告溢出。例如642报告伤害实际扣血340，统计340。伤害和受击量包含可确认的伤害事件生命损失；资源类扣血代价、治疗不混入或倒扣。受击总数须明确敌方攻击行动及命中证据；反伤/DOT等量可以记录，但不凭掉血另造攻击行动。
- 唯一获授权估算：真实HP数字缺失、明确满血、且该行动有明确击杀证据时，可按当时形态/已知等级、有生命个体E60、无生命性格估算。已知HPBefore、实际变化量、或明确满血加实测HPMax优先作实际数据；不忽略已有数值再套单生命。未知形态/等级/满血/击杀不估。估算单独标“估”，不写入原始HP、个体或性格；回合状态仍只重放原始数值。
- 应对成功为明确已执行应对分支，成功率为成功次数/明确的应对尝试次数，不平均逐局百分比。被打断的已知应对技能仍是一次尝试。只记录结果未知，不把没采到的选择当失败。被应对数按被敌方成功应对的我方行动去重，依靠明确group_ref等源关联，不根据自选目标或同回合相邻动作猜。

## 各指标分母

- 携带率：敌方阵容完整且身份已映射的有效对局。
- 实际登场：确认首发、明确换场或实际技能施放形成登场证据；后排受伤、治疗或被动成长不自动证明上场。使用行动完整样本，单局同种精灵多实例去重。
- 敌方技能发生率：仅该精灵实际登场且行动完整的对局。用过目标技能至少一次计1，多次仍1；没用计0；未登场或行动缺失不计。**这是观察到的使用发生率，不是真实携带概率。**
- 我方技能使用：实际施放次数/该精灵全部已确认技能施放次数，并列使用过此技能的有效对局比例。多段伤害、技能选择、预演不算多次施放。
- 首发率：明确且已映射首发的对局；条件首发率另取携带该精灵且首发已知的对局。队伍数组第一只、中途遇到的当前精灵不能代替首发。
- 组合：完整阵容包含所选全部精灵ID。名单按ID/形态判断，不猜“莎莎”等昵称。
- 属性分布：直接声明或条件下唯一的数值进入明确分类；多候选、缺值、同场同种不同实例不一致单列未知。每项有自己的有效样本数。

## 永久成长

按对局、阵营、实例、技能及触发规则分组。只使用 `kind: "growth"`、`phase: "executed"`、有明确 `trigger` 和角色归属的事件。

`stacks` 定义为**事件后的累计次数**，不是增量；1、2、3三个累计事件的当前次数是3，不是6。之后明确成长触发若没有stacks，只增加一次已观察触发。没有明确起始基数时不能把“已观察次数”宣称为整局总次数。

`skill`事件不通用地增加成长；例如能量刃需要应对成功，不能单凭施放次数计算。当前没有对未验证RKPP效果ID安装完整自动成长规则表，原始 `grow_times` 不等于战斗内永久成长。没有条件证据时显示未确认，不能填虚构层数。

## 性格与个体条件推断

详情中可补充已确认的单击伤害或同优先级先后关系，再“分析并保存候选”。所有条件写入独立战报，作为可追溯依据。

- 使用已知精灵ID、等级、资质，联合枚举有效个体0—60整数与性格0中性/1正/2负。
- 伤害条件需要确知对侧属性、最终威力、攻击方等级及减伤后倍率。最终威力已包含本系、克制和BUFF；不把它们再次乘入。
- 只接受未被剩余生命截断的单击普通伤害，不包含暴击、固伤、星陨或多段混合。防御修正需要已体现在输入的已知实际防御中；推断目标防御本身时要求不存在额外未知修正。
- 先后手要求同优先级、无其它速度修正；同速保留双方先后的可能性，不强行使用严格大于/小于。
- 未知等级/身份、条件缺失或冲突拒绝推断；直接记录不被猜测覆盖。只有所有可行联合解对某字段一致时，该字段才标“条件下唯一”。

- 已直接声明或唯一确定的属性自动应用。候选保留可查，须手动选择；缺失字段沿用该精灵当前个人配置作为明确标注的**手动假设**，不是战报事实。
- 有效个体用独立 `BattleMath.statFromEffectiveIV` 精算；42不能按“有个体”误变60。旧boolean API仍为0/60，旧公式与其它页面不变。
- 可编辑本次精确个体/性格/等级/技能；试算期间不写个人、编队或原手动技能累计。快照不自动应用未确认成长。
- 切页保留本次试算；“退出试算”恢复进入前的攻守与技能参数。普通搜索/历史等选择会先退出试算，再照原规则处理；重启不恢复快照。
- 本局数据不会替换现有编队。此前神谕鲨从编队重新载入编队配置是正确行为，没有改成读取个人配置。

### 规范化JSON

支持 `{ "version": 1, "records": [...] }`、单条记录、记录数组，以及逐行JSON。记录版本固定1；核心字段见 `battle_record_model.go`。

```json
{
  "version": 1,
  "id": "your-unique-battle-id",
  "mode": "unknown",
  "outcome": "unknown",
  "source": "manual-normalized",
  "quality": {"roster": {"me": false, "enemy": false}, "actions": false, "lead": {"me": false, "enemy": false}},
  "sides": {"me": {"pets": [], "before": {}, "after": {}}, "enemy": {"pets": [], "before": {}, "after": {}}},
  "events": [],
  "issues": []
}
```

上例仅是空结构说明，不是对局或测试数据。`id`与`instanceId`用字符串防止64位精度损失。时间必须带时区；`monsterId`是Wiki稳定ID，0表示未匹配，协议ID另存`protocolId`。`skillId`是Wiki技能ID，未匹配用0并保留`protocolSkillId`。人工映射只修改当前记录的未匹配项，不动全局主资料，也不默默替换已有非零映射。

个体/性格字段形如：

```json
{"value": 42, "certainty": "direct", "evidence": ["可核验的来源说明"]}
```

个体单位明确为有效0—60；性格为0/1/2。`candidate`应提供候选数组，`unknown`不填虚假value。规范化文件的完整性与direct标记都是**导入者声明**，不等于本程序已经对游戏现场独立验证。

### RKPP输入

原生导入器支持经过审阅的生命周期摘要，以及部分命名schema中的 `init_info/state_info`、双方pets和含明确对局ID上下文的perform条目。可以保留协议实例/精灵/技能ID、回合以及部分施放/效果/换场记录；不从中文摘要提取统计。

限制必须保留：

- 孤立perform帧没有可靠battle_id时不凭时间/最近一场猜归属；没有任意数字protobuf树自动解码。
- 原始协议ID与Wiki ID不同，未映射记录明确显示未知；人工确认仅针对当前记录。
- 当前读取的 `BattleDamageInfo` / `BattleHealInfo` 命名schema没有已验证的伤害量字段，`source_id`不是伤害量或可靠技能ID；不能用它填amount。原始字段待样本验证。
- `first_team/pos/enter_index`不当作首发证据；`nature/talent`单位/枚举未验证则不自动应用。
- 原始分数/胜负/排名等未验证语义保留未知，不把rank_order当排行榜名次。
- 部分分支、多目标归属、缺包或截断明确提示。实时流统一保持未验证完整性，不因为收到结束消息就成为完整统计样本。
- 直接导入PCAP或CSV不在本版解码器内；需先交给外部RKPP输出JSON/NDJSON。`opencode_summary.csv`文字不足以重建所有战斗事实。

## 实时模式与安全

页面连接用户已启动的本机 `/events`，不是启动Python或抓包。支持NDJSON及SSE数据帧，只允许带端口的HTTP loopback地址；`localhost`固定解析为127.0.0.1。不接受外网、凭据URL、代理、重定向、任意路径或压缩响应。

连接有超时、帧大小与接入数量限制；断流/不支持计数可见。读取→规范化→事务写入串行，停止/退出取消连接并等待后台结束。程序不会自动重连或重启抓取。

上游可能产生会话密钥、账号/IP、原始报文、解密明文文件；不要把这些当作可分享战报，也不要放入Git或安装包。本程序只存规范化白名单，不保存原包或密钥。UI导入上限8MiB；单记录1MiB；单批500场；统计快照上限10000场/64MiB，超过明确要求缩小范围，不截前N条伪装全量。

战报位于与个人配置相同应用数据根下的独立 `battle-records.sqlite`，首次访问战报数据端点才创建。schema版本/应用标记不符时拒绝操作，不清库；事务保证批量导入冲突整批回滚。时间索引先限制扫描范围，再由Go精确比较纳秒时间。数据写入请求参与原生关闭前等待。
